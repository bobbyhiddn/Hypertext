# Gemini image migration and consistency evaluation

Status: pre-evaluation implementation complete, 2026-08-21. Scheduled generation is disabled and **must stay disabled until every exit gate in this document passes**. Evaluation runs are manual only.

## Decision and official basis

Use `gemini-3.1-flash-image` as the candidate image model. Google's model page labels that exact model code **Stable**, and the image-generation guide calls it the versatile generalist in the current image family. It replaces this repository's preview identifier, `gemini-3.1-flash-image-preview`.

Official Google sources (checked 2026-08-21):

- [Gemini 3.1 Flash Image model](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-image) — stable model code and capabilities.
- [Gemini image generation guide](https://ai.google.dev/gemini-api/docs/image-generation) — supported models, Python/REST request shapes, reference-image guidance, aspect ratios, sizes, and response handling.
- [Gemini API libraries](https://ai.google.dev/gemini-api/docs/libraries) — current `google-genai` SDK.
- [Gemini API troubleshooting](https://ai.google.dev/gemini-api/docs/troubleshooting) — API errors and retry guidance.

The current API accepts text and image parts and returns generated image parts. With `generateContent`, request image output through `response_modalities`/`responseModalities` and set `image_config`/`imageConfig` for the `2:3` aspect ratio and `2K` size. SDK responses expose generated bytes on image parts as `inline_data`; REST responses use `inlineData.data` with an image MIME type. Authentication remains an API key supplied to `genai.Client(api_key=...)` or the `x-goog-api-key` header. Do not log keys or full failure payloads that may echo input content.

This migration changes the image model only. Text and review model selection needs a separate supported-model decision; do not silently replace those identifiers as part of the image rollout.

### Prompt and response flow

`pipeline/daily.py` builds card data from `templates/card_prompt_template.json`, writes each card's `card.json`, derives `prompt.txt` through `build_prompt_text`, and seeds `revise.txt`. Image phases pass `prompt.txt` to `hypertext.gemini.style` when references exist and otherwise to `hypertext.gemini.image`. Reference selection comes from `templates/card/` version/subtype template images and existing/example card PNGs. Review, rebuild, upgrade, revise, demo, batch, and example-card flows all return to the same image helpers. Lot generation has its own `templates/lot/prompt.txt` and `lots/generation.py` render/grade path. Template refinement reads global, version, and subtype `prompt.txt`/`revise.txt` files through `pipeline/template.py` and calls `cards.clean`.

Every image consumer assumes one usable image exists in the first candidate, scans its parts, accepts any `image/*` MIME type, and writes those bytes to a `.png` path without decoding to verify format, dimensions, or integrity. Basic generation permits interleaved text but ignores it; style generation requests image only. SDK and REST field spelling differ by design. Generation logs currently record references and prompt metadata but not an authoritative model ID or response MIME type.

Workflow entry points are `.github/workflows/daily-hypertext.yml` (manual plan/image generation), `daily-hypertext-continue.yml` (review/rebuild/upgrade/revise from PR comments), `demo-hypertext.yml`, `revise-hypertext.yml`, and both `template-refinement-*.yml` workflows. `deploy-gallery.yml` is a non-Gemini gallery build. Only the daily workflow previously had a cron trigger; it is now manual-only.

Existing automated coverage is only `package/test_package.py`, an import smoke test. Utility files named `test_style_*` are live, quota-consuming diagnostic scripts, not isolated tests, and must not run in CI or this evaluation without explicit manual authorization.

## Migration implementation

1. Introduce one `hypertext.gemini.config` module with `DEFAULT_IMAGE_MODEL = "gemini-3.1-flash-image"` and environment override `GEMINI_IMAGE_MODEL`. Make every image path consume it; remove endpoint-level and callable/CLI disagreement. Keep text and review constants separate.
2. Pin a tested lower bound for `google-genai` after verifying `Part.from_bytes`, `GenerateContentConfig`, `ImageConfig`, and response part behavior. Prefer the SDK for both basic and referenced generation, or keep a single tested REST adapter; do not maintain divergent behavior silently.
3. Build request/response helpers that validate supported aspect ratio and size, require a candidate image MIME type, base64-decode strictly when needed, decode bytes with Pillow, and verify the written output is exactly 1024x1536 or an explicitly documented 2K `2:3` size before downstream work. Record model, MIME type, dimensions, attempt count, and reference count in `generation.json`; never record secrets.
4. Add unit tests with fake SDK/HTTP responses for image-only, interleaved text/image, no candidates, safety/finish-only responses, invalid base64, wrong MIME type, corrupt bytes, wrong dimensions, transient errors, and permanent errors. Add a static test that rejects `-preview` image defaults and rejects a `schedule:` key in `daily-hypertext.yml`.
5. Update templates, utilities, metadata defaults, README, and workflow-provided model configuration in one consistency commit. Preserve per-card historical model metadata rather than rewriting generated history.
6. Run the evaluation below by manual dispatch in a non-production output directory. Keep generated evaluation artifacts out of the production queue/index and require a human to record the verdict.

Steps 1-5 are implemented on the revival branch. `google-genai>=1.40.0` is the
declared compatibility floor for `Part.from_bytes`, `GenerateContentConfig`,
`ImageConfig`, and response parts. Offline tests exercise those shapes without
API access. The shared contract treats `2:3` `2K` as exactly 1024x1536 PNG,
caps attempts at four, validates output before atomic publication, and writes
atomic non-secret success/failure metadata. Step 6 and all rollout gates remain
manual; no live diagnostic or generation run was performed during implementation.

## Consistency evaluation

Freeze one prompt, ordered reference list, model ID, `2:3` aspect ratio, and `2K` size per case. Generative output is not byte-deterministic, so deterministic checks validate contracts and card facts; visual consistency is a human gate. Generate three candidate images per case for both the current accepted baseline and candidate model, using the same inputs, then review blinded pairs.

Representative cards:

| Card | Coverage |
| --- | --- |
| `templates/example_cards/001-grace` | COMMON NOUN, basic frame and white rarity diamond. |
| `templates/example_cards/007-sanctify` | RARE VERB, pencil icon and one-card cost indicator. |
| `templates/example_cards/012-sacred` | GLORIOUS ADJECTIVE, sparkle-pencil icon and two-card cost indicator. |
| `templates/example_cards/013-moses` | COMMON NAME, quill icon and proper-name typography. |
| `templates/example_cards/020-messiah` | GLORIOUS TITLE, crown icon and most ornamented rarity treatment. |

Also run one template-clean edit and one revise/fix operation to cover image input/editing. Keep the exact reference set within the target model's documented limits.

Deterministic checks, required for every output:

- request manifest equals the frozen model, prompt hash, ordered reference hashes, `2:3`, and `2K` values;
- response has one decodable image part, an allowed image MIME type, expected portrait dimensions/aspect ratio, and no empty/corrupt output;
- card schema validation passes and rendered facts match `card.json`: word, type, rarity, five pips per stat, filled-pip counts, cost marker, ability, verse citations, Greek/Hebrew content, and trivia count;
- output naming, generation metadata, watermark verification, and gallery discovery pass without changing queue, stats, or indexes;
- retry tests prove only 429, 500, 502, 503, 504, timeouts, and connection failures retry; 400, 401, 403, safety blocks, malformed responses, and contract failures stop immediately.

Qualitative review is blind and uses two reviewers. Each candidate must receive pass/fail for template geometry, frame/palette match, correct type and rarity iconography, typography hierarchy, legibility of English/Greek/Hebrew, artwork relevance, absence of invented text/brackets/watermarks, and lack of style drift. A card passes when at least two of its three candidate outputs pass every critical category and both reviewers prefer or judge the candidate no worse than baseline. Disagreement goes to a third reviewer. All five cards plus both edit cases must pass; there is no average-score waiver.

## Retry, failure, and rollout gates

Use capped exponential backoff with jitter, honor numeric `Retry-After`, cap attempts at 4 for evaluation, and write an atomic failure record containing status/category/attempt count. Never retry authentication, invalid request/model, safety refusal, missing image, corrupt image, or dimension mismatch. Never fall back to another model automatically because that makes evaluation and provenance ambiguous. A failed card stops that case and leaves production state untouched.

Exit gates are: all unit/static tests pass; all deterministic checks pass; every representative and editing case clears qualitative review; costs and latency are recorded and accepted; model/provenance logging is verified; and an operator explicitly approves rollout. Until then, `.github/workflows/daily-hypertext.yml` must contain `workflow_dispatch` only and **scheduled generation must remain disabled**. After approval, first change production defaults and perform one supervised manual generation. Re-enabling cron is a separate, later operator decision and is not implied by migration approval.

## Deterministic template-cleanliness remediation (2026-08-22)

Inspection of the stat-pip comparison payloads and retained card renders found
two renderer-side causes of the remaining subtle inconsistency. The final
`hypertext.cards.polish` step was not a pixel operation: it submitted the entire
accepted card to Gemini again to remove hypothetical brackets. That second
generation could resample text masks and textured edges, producing pale subtitle
halos and small typography or spacing shifts. In addition, normal generation
could use up to three previously generated series cards as references, so the
reference set—and therefore geometry—changed with card order; revision paths
could also put the current, already-drifted card first.

Finalization is now byte-preserving and makes no API request. Brackets remain an
authoritative prompt and unchanged 100/100 review failure, rather than being
repaired by a destructive whole-image pass. Fresh, batch, rebuild, and revision
generation now default to checked-in matching examples plus the rarity template;
operator-supplied reference overrides still work, while generated series cards
are no longer implicit references. Focused regressions hash the complete PNG
(including high-contrast subtitle-edge pixels) and assert that default reference
selection cannot consult prior series renders. This does not claim a new live
seven-case pass and does not weaken any scoring gate. Scheduling remains disabled.

## End-to-end quality contract (2026-08-22)

The pipeline now defines `hypertext-quality/v1` across plan, prompt, references,
image request, candidate, composite, revision, and review. Each stage can record
input/output SHA-256 digests, status, a bounded attempt number (maximum four),
repair state, and timestamp in `outputs/quality-provenance.json`. A timeout or
missing image is a failure, never an output. The centralized image model remains
`gemini-3.1-flash-image`; this work produced no evidence supporting a model change.

Planning rejects missing identity, art, rarity/type, or stat fields and rejects
pips outside 0–5. Art prompt assembly asks Gemini for the illustration only and
forbids model-rendered typography, card numbers, metadata, badges, pips, frame,
UI, logos, and watermarks. Reference selection is deterministic and accepts only
prior 100/100 artifacts. Candidate selection considers only successful images and
uses stable original order to resolve equal contract scores.

Automated quality reports composition, typography, template fidelity, metadata
(including card number), stat pips, and artifact cleanliness. The weakest
dimension is the total score, so averaging cannot conceal a defect. Every
dimension must reach 100/100. Pipeline return codes that previously accepted
90/100 now fail below 100; the lower threshold remains useful only to choose
rebuild versus targeted repair. Repairs are limited to deterministic dimension
normalization, PNG conversion, pip redraw, and metadata rerender.

The representative zero-spend before/after packet is
[`docs/evidence/end-to-end-quality-before-after.md`](evidence/end-to-end-quality-before-after.md).
It reuses the four-card 2026-08-21 v4 run and pairs its historical artifacts with
offline regression evidence. This contract does not substitute for the five-card/
two-edit blinded study or operator rollout approval. Cron remains disabled.
